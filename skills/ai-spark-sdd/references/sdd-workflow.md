# 轻量 SDD 工作流与文件约定

本 Skill 是独立、通用的 Agent Skill，不依赖 GitHub Spec Kit CLI。参考 Spec-Driven Development 中 constitution → specify → clarify → plan → tasks → implement 的基本思想，但不虚构外部工具已安装。

## 文件职责

| 文件 | 目的 | 必须回答的问题 |
| --- | --- | --- |
| `AGENTS.md` | 指导 Coding Agent 的操作规范 | 到哪里读规格？按什么顺序开发？怎么验证？ |
| `docs/sdd/constitution.md` | 稳定的工程原则与禁止事项 | 哪些原则不能被随意破坏？ |
| `docs/sdd/spec.md` | 可验证的业务规格 | 为谁、解决什么、输入输出、边界、何为成功？ |
| `docs/sdd/plan.md` | 技术实现与架构 | 用什么简单可靠的方式实现？ |
| `docs/sdd/tasks.md` | 按顺序可交付的实现任务 | 第一步做什么、完成定义是什么？ |

## 一致性映射

- 核心功能需求 `FR-001`、`FR-002`……
- 每个需求至少关联一个可客观验证的 `AC-001`……
- 技术设计解释如何满足该需求（例如 `MOD-001` 或 `FR-001` 引用）
- 每个实现任务以 `T001`……编号，并标注相关 `FR-xxx` 与完成条件
- 范围外需求不要偷偷加进计划或任务；如果出现，先更新需求规格

## 轻量化原则

- 第一个 MVP 只需一个核心端到端场景，不要求企业级“全家桶”。
- 既有项目采用增量修改；避免未经用户许可覆盖旧版 `AGENTS.md` 或现存 specs。
- 对技术不熟练者，默认选择成熟栈、便于本地验证的实现形式；如果已有技术栈，优先兼容。
- 不提前设计并发集群、复杂角色权限、微服务，除非业务约束已明确证明必要。
- 所有关键业务规则都需至少一个“正常”样本与一个“异常/缺失数据”样本。

## 每个阶段的质量门禁

1. **Discovery**：能用非技术语言复述核心问题。
2. **MVP**：可以明确描述单次执行的输入、处理、输出、检查。
3. **Spec**：Must Have 的需求均有客观验收标准。
4. **Plan**：每个重要设计决策有依据，技术复杂度与 MVP 匹配。
5. **Tasks**：任务能逐项验证，并形成可运行的最小路径。
6. **Handoff**：参与者知道从哪个任务开始、准备哪些材料，以及如何看出结果对不对。

## 输出目录

```text
<project-root>/
├── AGENTS.md
└── docs/
    └── sdd/
        ├── constitution.md
        ├── spec.md
        ├── plan.md
        └── tasks.md
```

## 建议的提交方式

- 一次提交：建立 SDD v0.1 文档并确认范围。
- 之后按任务渐进提交，至少确保变更对应测试或可复核的验收。
- 需求调整时先修改 `spec.md`，再同步 `plan.md`、`tasks.md`，避免代码与需求脱节。
